## 1. Introduction

### 1.1 Purpose of the Document
This document describes the functional and non-functional requirements for the ESP32 Weather Station. It serves as a reference for the development, validation, and future extensions of the system.

### 1.2 Scope
The specification covers the acquisition of temperature, humidity, and air pressure data using a BME280 sensor, the display of this data on an SSD1306 OLED display, and the underlying software architecture based on FreeRTOS.

### 1.3 Target Audience
This document is intended for developers, testers, and anyone interested in gaining an in-depth understanding of the weather station.

## 2. Product Overview

### 2.1 Brief Description
The ESP32 Weather Station is a standalone device that continuously collects environmental data (temperature, humidity, air pressure) and displays it in real time on a small OLED screen. The system is robust, energy-efficient, and takes advantage of a real-time operating system (FreeRTOS) for reliable and responsive performance.

### 2.2 Goals and Vision
The main goal is to provide a weather station that is easy to build and use, delivers accurate measurements, and can serve as a foundation for further IoT projects.

## 3. Functional Requirements

### 3.1 Sensor Data Acquisition
*   **FR-1.1:** The system MUST acquire temperature readings from the BME280 sensor.
*   **FR-1.2:** The system MUST acquire humidity readings from the BME280 sensor.
*   **FR-1.3:** The system MUST acquire air pressure readings from the BME280 sensor.
*   **FR-1.4:** [CHANGED v1.4.0] The sensor data MUST be updated at the measurement interval set in sdkconfig (FR-3.2), 2 seconds by default. Before v1.4.0: "at least every 2 seconds".
*   **FR-1.5:** The system MUST provide a means to safely synchronize access to the I2C bus between different tasks (FreeRTOS mutex `i2cMutex`).
*   **FR-1.6** [v2.5.0]: The system MUST reject a sample whose values lie outside the operating range of the sensor, so that an impossible value never reaches the OLED, the serial log line of the measurement, MQTT, the history, the charts or the web page.
    *   **Range:** the operating range of the BME280 datasheet: temperature -40 to 85 °C, humidity 0 to 100 %RH, pressure 300 to 1100 hPa, limits included. The limits are in `main/config.h`.
    *   **Where:** in the driver, right after the compensation formulas and before the calibration offsets (FR-11.1) are applied: the check concerns what the chip measured. A calibrated value may therefore lie slightly outside the range (e.g. 85.5 °C with an offset of +1.0 °C).
    *   **Effect:** a rejected sample is a failed read (`ESP_ERR_INVALID_RESPONSE`), handled like an I2C error (NFR-2.2): the previous valid reading stays current, `MAX_CONSECUTIVE_ERRORS` failures in a row re-initialize the sensor (which also reloads its trimming parameters) and, while they persist, the OLED shows `SENSOR ERROR` and no measurement is published or stored. One valid sample ends the error state.
    *   **Cases covered:** a frame of all `0xFF` or all `0x00` bytes after a disturbance on the bus (with typical trimming parameters about 180 °C), a pressure of 0 returned by the compensation when the trimming parameters are corrupt (`p1 = 0`), and any other result outside the range. Before this requirement only the "measurement skipped" raw values (`0x80000`, `0x8000`) were rejected, and such samples were shown, sent, stored with a wrapped pressure value (unsigned 16-bit field, FR-10.6) and averaged into the charts.
    *   **Diagnosis:** each rejected sample is logged with `ESP_LOGW`, with the compensated values and the raw ADC values (temperature, pressure, humidity). `sys` (NFR-2.4) shows the number of samples rejected since start, next to the sensor (`rejected samples N`); it also counts the samples the chip reported as skipped, which were already rejected before.
    *   Values inside the range are not checked further: a jump between two consecutive samples is accepted.

### 3.2 Data Display on OLED
*   **FR-2.1:** The system MUST display the current temperature on the SSD1306 OLED display.
*   **FR-2.2:** The system MUST display the current humidity on the SSD1306 OLED display.
*   **FR-2.3:** The system MUST display the current air pressure on the SSD1306 OLED display.
*   **FR-2.4:** The OLED display MUST be refreshed at least once every second.
*   **FR-2.5:** The displayed values MUST be clearly legible and include the corresponding units (e.g. °C, %RH, hPa).
*   **FR-2.6:** [v1.3.0] The system MUST display an icon to indicate when a measurement arrives and disappear after 0.5s. The icon is a filled dot at the left edge of the OLED header; the display is redrawn as soon as a new measurement arrives. The duration is set in `main/config.h`.

### 3.3 Configuration
*   **FR-3.1:** [CHANGED v2.4.0] Since v2.4.0 the reference sea-level pressure is no longer a parameter: the altitude estimate it served was replaced by the sea-level pressure of FR-11.2, whose altitude is set via `idf.py menuconfig`. Configuration parameters such as display dimensions, I2C pins and addresses of the sensors and displays, and sea-level pressure MUST be defined centrally in a dedicated header file (`main/config.h`).
*   **FR-3.2:** [v1.4.0] Measurement interval time MUST be done in sdkconfig. It is set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_MEASURE_PERIOD_S`), in seconds, from 1 to 3600, default 2; `main/config.h` takes the value from there.

### 3.4 Error Handling
*   **FR-4.1:** The system MUST output an error message on the serial console (via `ESP_LOGE`) if the OLED display cannot be initialized.
*   **FR-4.2:** The system MUST output an error message on the serial console (via `ESP_LOGE`) if the BME280 sensor cannot be initialized.
*   **FR-4.3:** In the event of a critical initialization error (display or sensor), the system MUST remain in an error mode or stop operating.

### 3.5 Time of Day
*   **FR-5.1** [v1.1.0]: The system MUST obtain the current date and time from an NTP server (default `pool.ntp.org`) over Wi-Fi (station mode) and keep the clock synchronized periodically.
*   **FR-5.2** [v1.1.0]: The local time MUST use the time zone defined in `main/config.h` (default: UTC-3, Brasília, without daylight saving time).
*   **FR-5.3** [v1.1.0]: Once the clock is synchronized, the OLED header MUST show the date and time as `DD/MM/YYYY HH:MM`. Before synchronization, the header shows the title "WEATHER STATION". A sensor error ("SENSOR ERROR") takes precedence over the date and time.
*   **FR-5.4** [v1.1.0]: Once the clock is synchronized, every measurement written to the serial console MUST be prefixed with a timestamp in the format `YYYY-MM-DD HH:MM:SS`.
*   **FR-5.5** [v1.1.0]: Wi-Fi or NTP failures MUST NOT be critical errors: the weather station MUST keep measuring and displaying, log a warning (`ESP_LOGW`), and retry the Wi-Fi connection periodically (every 10 s by default).
*   **FR-5.6** [v1.1.0, CHANGED v2.6.0]: Since v2.6.0 the menuconfig values are factory defaults: a set stored by the setup page replaces them (FR-12.1), and a station without an SSID starts in setup mode (FR-12.2) instead of running without Wi-Fi. The Wi-Fi credentials (SSID and password) MUST be set via `idf.py menuconfig` ("Weather Station" menu) and stored only in the local `sdkconfig`, which is not version-controlled. With an empty SSID, Wi-Fi and the time of day are disabled.
*   **FR-5.7** [v1.2.0]: The OLED header MUST show a Wi-Fi icon at its right edge: 1 to 3 arcs according to the signal strength (3 arcs at RSSI ≥ -60 dBm, 2 arcs at ≥ -70 dBm, 1 arc below; thresholds in `main/config.h`) while connected, and an X while disconnected. With no SSID configured, no icon is shown. The header text is centered in the space left of the icon.
*   **FR-5.8** [v2.2.0]: The station MUST report the Wi-Fi signal strength (RSSI of the access point, in dBm) with its data, so the quality of the link at its location can be followed over time and correlated with failures.
    *   The RSSI is sampled with every measurement (FR-3.2) while Wi-Fi is connected.
    *   **MQTT:** each data message (FR-6.3, FR-10.4) adds `rssi_dbm`, an integer: the lowest RSSI sampled since the previous message, so short drops of the signal between two publishes are not hidden. The field is left out when no sample was taken in the interval. Example: `{"device_id":"ws-a0b76551a842","sensor_id":"bme280-3fa91c07","time":1792161125,"temperature_c":23.41,"humidity_rh":56.12,"pressure_hpa":1012.84,"rssi_dbm":-67}`. The RSSI belongs to the station, not to a sensor: it is not a sensor channel (FR-10.3) and is not listed in the info message.
    *   **Web:** `/api/current` (FR-8.3) adds `rssi_dbm`, the current RSSI, `null` while Wi-Fi is not connected. The page (FR-8.2) shows it in dBm, e.g. `-67 dBm`, on a line of its own below the status line; both lines are aligned to the right, so the Wi-Fi signal bars at the end of the status line stand at the right edge, with the RSSI below them. This helps when placing the station.
    *   The RSSI is **not** stored in the measurement history (FR-7.1, FR-10.6): the record format, `log dump`, `/history.csv` and the web charts stay unchanged. The record has no free byte, and storing the RSSI would need a new history format; long-term series of the RSSI are left to the MQTT consumers.
    *   Changes FR-6.3, FR-8.2 and FR-8.3.

### 3.6 Data Transmission (MQTT)
*   **FR-6.1** [v1.5.0]: The system MUST transmit the weather data over Wi-Fi to an MQTT broker (MQTT 3.1.1; `mqtt://` or `mqtts://` URI). This implements the "Wi-Fi connectivity" extension proposed in section 7 up to v1.4.0.
*   **FR-6.2** [v1.5.0]: The latest valid measurement MUST be published at the publish interval set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_MQTT_PUBLISH_PERIOD_S`), in seconds, from 1 to 86400, default 60. The interval is independent of the measurement interval (FR-3.2). A measurement that was already published is not sent again, and nothing is sent while the sensor has no valid reading.
*   **FR-6.3** [v1.5.0, CHANGED v2.0.0, CHANGED v2.2.0, CHANGED v2.4.0]: Since v2.4.0 each message also carries `pressure_msl_hpa`, the pressure reduced to sea level (FR-11.2), and `dew_point_c` (FR-11.3, left out when there is none); `pressure_hpa` stays the station pressure, and all values are calibrated (FR-11.1). Since v2.2.0 each message also carries `rssi_dbm`, the lowest Wi-Fi RSSI since the previous message (FR-5.8). Since v2.0.0 each message also carries `device_id` and `sensor_id` (FR-10.4). Before v2.0.0: Each message MUST be a JSON object with the fields `temperature_c`, `humidity_rh` and `pressure_hpa` (two decimal places) and, once the clock is synchronized (FR-5.1), `time` with the Unix time of the measurement in seconds. Example: `{"time":1792161125,"temperature_c":23.41,"humidity_rh":56.12,"pressure_hpa":1012.84}`.
*   **FR-6.4** [v1.5.0, CHANGED v1.8.8, CHANGED v2.0.0]: Since v2.0.0 messages go to the topic of the station, `weather-station/<device_id>/data` (prefix in `main/config.h`), and the station publishes an info message (FR-10.4); QoS and retain flag are unchanged. Before v2.0.0: Messages MUST be published to the topic defined in `main/config.h` (default `weather-station/data`) with QoS 1 and the retain flag set, so a new subscriber receives the latest reading at once. With QoS 1 the broker confirms each message, and a message not yet confirmed when the connection drops is sent again after the reconnection (messages older than 30 s are dropped; the flash history keeps every reading). Before v1.8.8: QoS 0, so a reading in transit when the connection dropped was lost for MQTT.
*   **FR-6.5** [CHANGED v1.7.1, CHANGED v1.8.7, CHANGED v1.8.8, CHANGED v2.0.1]: MQTT failures MUST NOT be critical errors: the weather station MUST keep measuring and displaying, log a warning (`ESP_LOGW`), skip the publish while disconnected, and reconnect to the broker automatically. While Wi-Fi has an IP address, a failed connection is retried every 10 s by default; while Wi-Fi is down, no connection is attempted; when Wi-Fi gets an IP address again, the client reconnects at once. Since v1.8.7 the MQTT keepalive is 30 s (`main/config.h`), so a connection that stops delivering is noticed after about 45 s; before, the ESP-MQTT default of 120 s took up to 3 minutes. Since v1.8.8 the keepalive is 60 s: a dead connection is noticed after about 90 s, and stalls of up to about 30 s (seen on the path to the broker) no longer force a reconnection, as they did with 30 s. Since v2.0.1 a send to the broker may wait up to 30 s for the link (`MQTT_NETWORK_TIMEOUT_MS` in `main/config.h`) before the connection is dropped; before, the ESP-MQTT default of 10 s dropped the connection when a stall of the link (seen at about -65 dBm) hit the resend of an unconfirmed message (`Writing didn't complete in specified timeout`). Before v1.7.1: "reconnect to the broker automatically (every 10 s by default)", which also tried, and logged errors, while Wi-Fi was down, and waited up to 10 s after Wi-Fi returned.
*   **FR-6.6** [v1.5.0, CHANGED v2.6.0]: Since v2.6.0 the menuconfig values are factory defaults: a set stored by the setup page replaces them (FR-12.1). The broker URI, user name and password MUST be set via `idf.py menuconfig` ("Weather Station" menu) and stored only in the local `sdkconfig`, which is not version-controlled. With an empty broker URI, or without Wi-Fi (FR-5.6), data transmission is disabled.
*   **FR-6.7** [v2.1.0]: The station MUST publish its online status to `weather-station/<device_id>/status` (QoS 1, retained): `online` on every connection to the broker, and `offline` as its MQTT last will, which the broker publishes when the connection drops or the station stops answering (after about 1.5 keepalive periods, 90 s with the keepalive of FR-6.5). A management system sees at once which stations are reachable by subscribing to `weather-station/+/status`. The payloads are defined in `main/config.h`. This implements the "Online status" extension proposed in section 7 up to v2.0.1.

### 3.7 Measurement History
*   **FR-7.1** [v1.6.0]: The system MUST store a history of the measurements in the internal flash, in the 5 MB data partition `history` defined in `partitions.csv`. This implements the "Data logging" extension proposed in section 7 up to v1.5.0 (internal flash option; no SD card). The partition table keeps the offsets of `nvs` and `phy_init` and enlarges the app partition from 1 MB to 2 MB.
*   **FR-7.2** [v1.6.0]: The latest valid measurement MUST be stored at the log interval set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_LOG_PERIOD_S`), in seconds, from 1 to 86400, default 60. The interval is independent of the measurement and publish intervals. A measurement is stored only once, and nothing is stored while the sensor has no valid reading.
*   **FR-7.3** [v1.6.0, CHANGED v2.0.0]: Since v2.0.0 the records are in format 2 (FR-10.6): each sector names the device and the sensors, and each measurement its sensor; capacity 325,120 measurements, about 7.4 months at 60 s. Before v2.0.0: Each record MUST hold a sequence number, the Unix time of the measurement (0 before the clock is synchronized), the temperature (0.01 °C), the humidity (0.01 %RH), the pressure (0.1 hPa) and a CRC16. The history works as a ring buffer: when it is full, the oldest 4 KB sector (256 records) is erased. Capacity: 327,680 records, about 7.5 months at 60 s. The history survives restarts and power loss; a record cut short by a power loss is discarded.
*   **FR-7.4** [v1.6.0, CHANGED v2.0.0]: Since v2.0.0 the CSV columns are `device_id,sensor_id,seq,time,temperature_c,humidity_rh,pressure_hpa`, and `log info` also shows the format version, the device and the sensors (FR-10.6). Before v2.0.0: The history MUST be readable on the serial console (prompt `weather> `, 115200 baud): `log info` shows the number of records and the space used; `log dump [N]` prints the last N records (all if N is omitted), oldest first, as CSV with the columns `seq,time,temperature_c,humidity_rh,pressure_hpa`, where `time` is local time `YYYY-MM-DD HH:MM:SS` (empty if unknown). Other log output is suppressed during the dump. `help` lists the commands.
*   **FR-7.5** [v1.6.0]: The command `log clear` MUST erase the whole history.
*   **FR-7.6** [v1.6.0]: History failures MUST NOT be critical errors: if the partition is missing or a write fails, the system logs a warning (`ESP_LOGW`) and keeps measuring, displaying and publishing.

### 3.8 Web Page
*   **FR-8.1** [v1.7.0]: The system MUST serve a web page on the local network over HTTP (port 80), reached by the IP address of the station. The server starts once Wi-Fi has an IP address, and the URL (`Web page at http://<ip>/`) is logged on the serial console on every connection. There is no name resolution (mDNS) and no password: the page is read-only and offers no action that changes the station. This implements the "Web server" extension proposed in section 7 up to v1.6.0.

### 3.10 Identification
This section gives every station, every sensor and every measurement an identifier, so a management system can tell stations and sensors apart and keep the data of several stations together. It breaks compatibility with v1.x in two places: the MQTT topic (FR-10.4) and the history format (FR-10.6); the requirements it changes are named in each item and marked `[CHANGED v2.0.0]`.

*   **FR-10.1** [v2.0.0]: Each station MUST have a unique, permanent device identifier derived from the factory base MAC address in eFuse (the Wi-Fi station MAC): `ws-` followed by all 6 bytes in lowercase hex, e.g. `ws-a0b76551a842`. It does not change with firmware updates, reflashing, erasing NVS or changing the Wi-Fi settings. It is logged at boot and shown by `sys` (NFR-2.4). The MQTT client ID becomes the device identifier (section 6.4; before: `weather-station-` plus the last 3 bytes of the MAC address).
*   **FR-10.2** [v2.0.0, CHANGED v2.6.0]: Since v2.6.0 the name can also be set on the setup page (FR-12.1); the menuconfig value is the factory default. The user MAY give the station a free-text name (e.g. "Varanda") via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_DEVICE_NAME`, up to 32 characters, default empty). The name is for people only and is never used as a key; it is shown by `sys`, in the MQTT info message (FR-10.4) and on the web page (FR-10.5).
*   **FR-10.3** [v2.0.0]: Each sensor MUST have an identifier that tells physical chips apart: its type followed by the CRC-32 (IEEE 802.3) in lowercase hex of its factory trimming parameters, e.g. `bme280-3fa91c07`. For the BME280 these are `dig_T1` to `dig_H6` (32 bytes: registers `0x88`–`0x9F`, `0xA1` and `0xE1`–`0xE7`), which the driver already reads at initialization. The BME280 has no serial number; the trimming parameters differ from chip to chip, but the manufacturer does not guarantee that they are unique. Each sensor also has a position: its index in the station configuration (`main/config.h`, 0 for the BME280) and its bus address (`i2c@0x76`); the position names the measuring point, the identifier the chip. Each quantity a sensor measures is a channel with a fixed identifier (`temperature`, `humidity`, `pressure`). The full identifier of a channel is `<device_id>/<sensor_id>/<channel>`, e.g. `ws-a0b76551a842/bme280-3fa91c07/temperature`.
*   **FR-10.4** [v2.0.0, CHANGED v2.4.0]: Since v2.4.0 the info message also holds `altitude_m` (FR-11.2) and, per channel, `offset` (FR-11.1), and is published again after every calibration change. MQTT messages MUST be published per station. Changes FR-6.3 and FR-6.4.

With several stations on one broker, each keeps its own retained reading; before v2.0.0 all stations published to `weather-station/data` and overwrote each other's retained message.

A management system finds every station and its sensors by subscribing to `weather-station/+/info`.

Every record starts with a 24-bit sequence number (compared modulo 2^24; it restarts at 0 after 16,777,216 records, far more than the history holds) and a type byte: the sensor index (0 to 253) for a measurement, `0xFE` for a control record; `0xFF` is never used, as in erased flash.

Such sectors are ignored (not read, not counted) and erased when the ring buffer reaches them, or by `log clear`; at start-up their number is logged as a warning (`ESP_LOGW`). Erasing them all at once would delay the start by up to a minute. The history of a v1.x station MUST be downloaded (`/history.csv`) before updating. A firmware before v2.0.0 cannot read format 2; going back requires `log clear`.
*   **FR-10.7** [v2.0.0]: The station MUST detect a sensor replacement. At start-up and on every re-initialization of a sensor (after I2C errors), it compares the sensor identifier with the last one stored in NVS for that position. ### 3.11 Measurement Quality
This section makes the readings comparable with those of other stations and weather services: a correction for the error of the individual chip and its mounting, the pressure reduced to sea level, the dew point, and a check of the pressure against a nearby airport. The stored history keeps the station pressure (the physical measurement); derived values are computed when they are shown or sent.

*   **FR-11.1** [v2.4.0]: The user MUST be able to calibrate each channel of a sensor with an offset that is added to every reading. This implements the "Calibration" extension proposed in section 7 up to v2.3.5.
    *   One offset per channel: temperature in 0.01 °C, humidity in 0.01 %RH, pressure in 0.1 hPa (the resolutions of the history, FR-10.6). Limits in `main/config.h`, by default ±5.00 °C, ±10.00 %RH and ±10.0 hPa; a value outside the limits is refused. Default 0 (no correction). A temperature offset also compensates the self-heating of the sensor inside an enclosure.
    *   The offsets are applied in `taskMeasure` right after the compensation formulas, so the OLED, the serial log, MQTT, the history, the charts and the web page all show the calibrated value. The humidity is clamped to 0–100 %RH after the offset.
    *   Console command `cal` (FR-7.4 prompt): `cal` shows the sensor identifier and the three offsets; `cal set <temperature|humidity|pressure> <offset>` sets one offset in the unit of the channel (e.g. `cal set temperature -1.25`); `cal clear [channel]` resets one offset, or all of them, to 0. A change takes effect with the next measurement and is logged (`ESP_LOGI`, channel, old and new offset). The web page and MQTT do not offer calibration: the web page stays read-only (FR-8.1).
    *   The offsets are stored in NVS per sensor position, together with the sensor identifier they were set for (FR-10.3), and survive restarts and firmware updates. The calibration belongs to the chip: when the identifier at a position changes (FR-10.7), its offsets are reset to 0 with a warning (`ESP_LOGW`) that names the discarded offsets.
    *   **History:** a new control record (format 2, FR-10.6), kind 3, **calibration**: sensor index, then the three offsets as signed 16-bit values in the channel resolution. It is written when an offset changes, before the next measurement, and after the sensor definitions at the start of every sector while any offset is not 0, so every sector still describes itself. The format version stays 2: readers since v2.0.0 ignore control kinds they do not know. With one calibrated sensor, 3 records per sector are control records: capacity 323,840 measurements, still about 7.4 months at 60 s. `log info` also shows the latest calibration per sensor; `log dump` and `/history.csv` are unchanged (their values are already calibrated).
    *   **Info message** (FR-10.4) and `/api/info` (FR-10.5): each channel also carries `offset`, a number in the unit of the channel (e.g. `-1.25`). The info message is published again after every change.
    *   **Web page:** `/api/current` holds the offsets as `calibration` (FR-8.3); when any offset is not 0, the footer shows `calibrated` next to the sensor identifier, with the offsets as a tooltip.
*   **FR-11.2** [v2.4.0, CHANGED v2.6.0]: Since v2.6.0 the altitude can also be set on the setup page (FR-12.1); the menuconfig value is the factory default. The station MUST report the air pressure reduced to mean sea level (QNH), as weather services and other stations do. Changes FR-3.1, FR-6.3, FR-8.2, FR-8.3 and FR-8.4.
    *   The altitude of the station is set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_ALTITUDE_M`), in metres, from -500 to 9000, default 0 (sea level: the reduced pressure equals the station pressure).
    *   Reduction with the ICAO standard atmosphere: `p_msl = p × (1 − 2.25577·10⁻⁵ × h)^(−5.25588)`, where `p` is the calibrated station pressure (FR-11.1) and `h` the altitude. It does not use the measured temperature, which is the indoor or enclosure temperature and would make the value drift with the heating. For a given altitude the reduction is a constant factor, computed once at start-up.
    *   **OLED:** the pressure row shows the sea-level pressure. **Serial log:** each measurement line shows the station pressure and the sea-level pressure; the altitude estimate (`Alt~… m`) and the constant `SEA_LEVEL_PRESSURE_HPA` in `main/config.h` are removed (changes FR-3.1).
    *   **MQTT** (FR-6.3): each data message adds `pressure_msl_hpa` (two decimal places); `pressure_hpa` stays the station pressure. **Info message** (FR-10.4) and `/api/info`: add `altitude_m`.
    *   **Web:** `/api/current` (FR-8.3) adds `pressure_msl_hpa`. The page shows the sea-level pressure as the main pressure value (card label `Pressure (sea level)`) and, when an altitude is set, the station pressure in small type below it (e.g. `station 921.4 hPa`); at altitude 0 both are equal and only one is shown. The pressure chart (FR-8.4) shows the sea-level pressure by applying the factor to its points; `/api/charts` and `/api/history` add `altitude_m` so the page can apply it.
    *   **History** (FR-10.6), `log dump` and `/history.csv` keep the station pressure, unchanged: it is the measurement, and the sea-level value can be computed from it with `altitude_m` of the info message.
*   **FR-11.3** [v2.4.0]: The station MUST report the dew point, computed from the calibrated temperature and humidity (FR-11.1). Changes FR-6.3, FR-8.2 and FR-8.3.
    *   Magnus formula over water with the constants of Sonntag (1990), `b = 17.62`, `c = 243.12 °C`: `γ = ln(RH/100) + b·T/(c + T)`, `Td = c·γ/(b − γ)`. Valid from -45 to 60 °C, with an error below 0.35 °C in that range; outside the range, or at a humidity of 0, no dew point is given.
    *   **MQTT** (FR-6.3): each data message adds `dew_point_c` (two decimal places); the field is left out when no dew point is given. **Web:** `/api/current` (FR-8.3) adds `dew_point_c` (`null` when none is given), and the page shows it in small type below the humidity, e.g. `dew point 14.2 °C`. **Serial log:** each measurement line adds `Td=…`.
    *   The OLED is unchanged: its three value rows fill the display (FR-2.x). The dew point is not stored in the history and has no chart; it can be computed from the stored temperature and humidity.
*   **FR-11.4** [v2.4.0, CHANGED v2.6.0]: Since v2.6.0 the airport can also be set on the setup page (FR-12.1), so the METAR code is always part of the firmware; with no airport `taskMetar` is not created and no request leaves the station, as before. The station MUST check its sea-level pressure (FR-11.2) against the QNH of a nearby airport (METAR) and report the difference, so an error of the altitude or of the sensor is found without manual comparison. It only reports: it never changes the altitude or the calibration (FR-11.1) on its own. Depends on FR-11.1 and FR-11.2.
    *   **Configuration:** the ICAO code of the airport is set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_METAR_STATION`, 4 characters, e.g. `SBGR`, default empty). With an empty code, or without Wi-Fi (FR-5.6), the check is disabled and no request leaves the station. The user picks the airport: preferably less than about 50 km away and with no mountain range in between. The service URL (`https://aviationweather.gov/api/data/metar?ids=<code>&format=json`) and all limits below are in `main/config.h`.
    *   **Retrieval:** a task of its own, `taskMetar` (module `metar.h` / `metar.cpp`), created only when the check is enabled, fetches the METAR over HTTPS (`esp_http_client`, server certificate checked with the ESP-IDF certificate bundle) once per hour at minute 10, and only while the clock is synchronized (FR-5.1). Each request carries a User-Agent of its own, `esp32-weather-station/<firmware version>`, as the API asks of automated clients (no identifier of the station); the API allows 100 requests per minute, the station makes 2 per hour at most. The answer is limited to 2 KB; from it the station uses `icaoId`, `obsTime`, `altim` (QNH in hPa; airports that report in inches of mercury, `A` group, get it converted with a decimal) and `rawOb`. When the observation is not newer than the last one used, or the API answers `204 No Content` (no recent observation), it tries once more at minute 25. Before each request it checks the largest free heap block (FR-8.9); below 48 KB the request is skipped with a warning (`ESP_LOGW`), because the TLS handshake needs about 40 KB. Timeouts (10 s), errors and unusable answers are logged as warnings and never critical (as FR-5.5); the next attempt follows at the next hour, with no faster retries.
    *   **Sample:** an observation is used when its `altim` lies between 850 and 1090 hPa and the 1-hour chart period (FR-8.4, 1-minute buckets) holds a measurement within ±2 minutes of `obsTime`. The station QNH at that time is the mean of those buckets reduced as in FR-11.2. The METAR gives the QNH in whole hPa, rounded down (ICAO Annex 3): when `rawOb` carries a `Q` group, 0.5 hPa is added to `altim` to remove that bias. The sample is `difference = station QNH − reference QNH`, in hPa.
    *   **Window:** the last 168 samples (7 days) are kept in RAM, in a ring; they are lost at a restart, and the ring is emptied when the pressure offset changes (FR-11.1), since the older samples no longer apply. The **median** of the window is reported once it holds at least 24 samples: unlike the mean, it ignores the hours in which a front lies between the station and the airport.
    *   **Suggestion:** with the median, the station computes two alternative corrections, since a constant difference can come from either and the two cannot be told apart: the pressure offset that would cancel it (the value to give to `cal set pressure …`: the current offset minus the median divided by the reduction factor of FR-11.2, rounded to 0.1 hPa), and the altitude that would cancel it (the altitude at which the reduction of FR-11.2 gives the reference QNH, rounded to 1 m). The user applies one of them: the altitude first when it comes from an unreliable source, the offset when the altitude is known.
    *   **Warning:** when the median exceeds ±2.0 hPa, a warning is logged (`ESP_LOGW`, airport, median, number of samples and both suggestions); it is logged again only after the median has come back within the limit.
    *   **Interfaces:** `sys` (NFR-2.4) shows the airport, the last observation (time, reference QNH, difference), the median and the number of samples, and the suggestions. After each sample a retained message (QoS 1) goes to `weather-station/<device_id>/metar`: `{"station":"SBGR","obs_time":1794409200,"qnh_ref_hpa":1025.5,"qnh_hpa":1026.3,"diff_hpa":0.8,"median_diff_hpa":1.1,"samples":96,"suggested_offset_hpa":-1.0,"suggested_altitude_m":736}` (the median and the suggestions are `null` below 24 samples). `/api/current` (FR-8.3) adds the same object as `metar`, `null` while the check is disabled or has no sample, and the page footer shows e.g. `METAR SBGR: +1.1 hPa (median of 96)`. Changes FR-8.3 and NFR-2.4.
    *   Nothing is written to the history (FR-10.6) or to NVS. The request reveals the public IP address of the network and the chosen airport to the service; no identifier of the station is sent.
    *   Adds the ESP-IDF components `esp_http_client` and `esp-tls` with the certificate bundle (section 5.2). A consumer of MQTT with access to the internet can perform the same check without this requirement, using `pressure_hpa`, `pressure_msl_hpa` and `altitude_m` (FR-11.2).

### 3.12 Provisioning
This section lets the station be installed without a development environment: the Wi-Fi network, the MQTT broker and the other per-installation settings are entered from the browser of a phone, over a Wi-Fi access point that the station opens for that purpose. Bluetooth is not used: the official provisioning apps only send the Wi-Fi credentials, and a browser needs no app on any phone. The values of `idf.py menuconfig` remain the factory defaults, so development works as before.

*   **FR-12.1** [v2.6.0]: The station MUST keep its per-installation settings in NVS, where they can be changed without a new firmware build. Changes FR-5.6, FR-6.6, FR-10.2, FR-11.2 and FR-11.4.
    *   **Settings:** Wi-Fi SSID and password (FR-5.6); MQTT broker URI, user name and password (FR-6.6); station name (FR-10.2); altitude (FR-11.2); METAR airport (FR-11.4). The intervals (measurement, publish, log) and the display switch-off time stay in menuconfig only.
    *   **Source:** the settings are stored together, as one set (NVS namespace `settings`). While no set is stored, the station uses the values of `idf.py menuconfig`, as before; once a set is stored, it replaces all of them, and a later change in menuconfig has no effect until the set is erased (FR-12.6). The source in use (`stored` or `menuconfig`) is logged at start and shown by `sys` (NFR-2.4).
    *   **Effect:** the settings are read at start. Every module that used the menuconfig constants (`net_time`, `telemetry`, `identity`, `quality`, `metar`) reads them from the active set instead; the sea-level factor (FR-11.2) is computed at start from the active altitude, and `taskMetar` is created when the active set names an airport, so the METAR code is always part of the firmware (about 90 KB of flash, section 5.2).
    *   **Limits**, checked on every save: SSID 1 to 32 bytes; Wi-Fi password empty (open network) or 8 to 63 characters; broker URI empty (transmission off) or starting with `mqtt://` or `mqtts://`, up to 128 characters; MQTT user name and password up to 64 characters; name up to 32 characters (FR-10.2); altitude -500 to 9000 m; METAR airport empty or 4 letters (stored in capitals). The limits are in `main/config.h`.
    *   Changing the settings never touches the history (FR-7.x), the calibration (FR-11.1) or the identifiers (FR-10.1, FR-10.3). The info message (FR-10.4) carries the new name and altitude after the restart that applies them.

*   **FR-12.2** [v2.6.0]: The station MUST enter a setup mode in which it offers the settings for editing, and leave it on its own. Changes FR-9.1.
    *   **Entry:** (a) at start, when the active set has no SSID (a new station); (b) when the BOOT button is held for 5 s (`main/config.h`) at any time: a shorter press keeps switching the display on and off (FR-9.1), and the press that started the hold may have switched it off; (c) with the console command `setup` (FR-12.6). A station whose network is merely unreachable does not enter setup mode by itself, so an outage of the router never opens an access point.
    *   **During setup mode:** measuring, the display and the history continue (FR-1.x, FR-7.2). The connection to the configured network is dropped, so MQTT goes `offline` through its last will (FR-6.7) and nothing is published; the normal web page (FR-8.1), the METAR check (FR-11.4) and the network watchdog (NFR-2.3) are suspended, so the watchdog does not restart the station.
    *   **Exit:** after a successful save (FR-12.5), the station restarts with the new settings. Without a save it returns to normal operation with the old settings when a second 5-second hold of BOOT or `setup cancel` ends the mode, or after 15 minutes (`main/config.h`) during which no device was connected to its access point. A new station without an SSID stays in setup mode.
    *   Entry and exit are logged with their cause (`ESP_LOGI`).
    *   **Restarts:** setup mode is entered and left through a restart (a flag in RTC memory, which survives a software restart, tells the next start which mode to run), so the network of normal operation is never torn down while running. Measuring pauses for the 2 to 3 s of each restart, and what is lost at any restart is lost here too: the METAR window (FR-11.4) and the clock synchronization; measurements stored during setup mode carry no time (0, FR-7.3) unless the clock was synchronized again.

*   **FR-12.3** [v2.6.0]: In setup mode the station MUST open a Wi-Fi access point of its own, and the OLED MUST show how to reach it.
    *   **Access point:** WPA2-PSK on channel 1, named `ws-setup-` followed by the last 2 bytes of the MAC in lowercase hex (e.g. `ws-setup-f480`), one client at a time; address `192.168.4.1`, with DHCP for the client. The password is 8 random characters (digits and lowercase letters without `0`, `o`, `1`, `l`), new at every entry, so only someone who can read the display or the serial console can join. The station keeps its station interface (mode AP+STA) to scan for networks and to test new credentials (FR-12.5).
    *   **Captive portal:** a DNS server on the access point answers every name with `192.168.4.1`, and the setup page answers any address, so most phones open it by themselves after joining; otherwise the user opens `http://192.168.4.1/`.
    *   **Display:** while in setup mode the display stays on (FR-9.2 does not apply) and shows, instead of the measurements: `SETUP` in the header, the network name, the password and `192.168.4.1`. The same lines are logged on the serial console at entry.

*   **FR-12.4** [v2.6.0]: In setup mode the station MUST serve a setup page at `http://192.168.4.1/` to edit the settings of FR-12.1.
    *   **Content:** the device identifier, the firmware version and the source of the active settings; the Wi-Fi networks found by a scan (name, signal in dBm and whether it is protected, strongest first, at most 20, scanned again on request) to pick from, and a field for a hidden network; the Wi-Fi password; the MQTT broker URI, user name and password; the station name, the altitude and the METAR airport. Each field is filled with the active value, except the passwords.
    *   **Passwords:** never sent to the browser, never logged and never shown by `sys`. An empty password field keeps the stored password; a check box clears it (open network, broker without password).
    *   **Form:** one HTML file embedded in the firmware like the web page (section 6.5), without external resources, usable on a phone screen; the same input limits as FR-12.1 are checked in the page and again by the station.
    *   **Addresses:** `/` (the page, `setup_page.html`), `/api/settings` (the active settings without the passwords, and the limits), `/api/scan` (the networks; `?refresh=1` scans again), `/api/save` (POST, form-encoded; answers at once and starts the test of FR-12.5), `/api/status` (state of the test: `idle`, `testing_wifi`, `testing_broker`, `saved`, `failed`, with a message); any other address is redirected to `/`.
    *   The normal web page stays read-only and offers no settings (FR-8.1); the setup page exists only in setup mode, on the access point.

*   **FR-12.5** [v2.6.0]: Saving MUST test the new Wi-Fi credentials before storing them, so a typing error does not leave the station unreachable.
    *   On "Save", the station checks the limits, then connects its station interface to the chosen network while the access point stays open (both use the channel of the chosen network; the phone may lose the connection for a moment and reconnects to the access point by itself). The page shows the progress and the result within 30 s: connected with the IP address obtained, wrong password, network not found, or no IP address.
    *   **Success:** with a broker URI, the station also tries the broker for up to 10 s and shows the result (connected, refused with the reason, or not reached). The set is then stored, whatever the broker result: a broker can be down at installation time. The page shows the IP address under which the normal web page will be reached, and the station restarts 5 s later.
    *   **Failure of the Wi-Fi test:** nothing is stored; the page keeps the entered values (except the passwords) and shows the cause, and the station stays in setup mode.
    *   The phone has to join its usual network again by itself after the restart; the page says so.

*   **FR-12.6** [v2.6.0]: The serial console MUST offer the command `setup`: `setup` enters setup mode, `setup cancel` leaves it without changes, `setup show` lists the active settings and their source with the passwords masked (`***` when set, empty otherwise), and `setup clear` erases the stored set, after which the station restarts with the values of menuconfig (a new station without an SSID enters setup mode). `setup clear` touches nothing else: history, calibration and sensor records stay.

*   **FR-12.7** [v2.6.0]: Security of provisioning.
    *   Settings can be changed only by someone with physical access: the access point appears only after a button press at the station, the console command or on a new station, and its password is shown only on the display and the serial console.
    *   The setup page is served over HTTP inside the WPA2 network of the access point; the passwords travel only from the browser to the station.
    *   The settings are stored in NVS without encryption, as the menuconfig values were stored in the firmware image before; whoever can read the flash of the board can read them.

## 4. Non-Functional Requirements

### 4.1 Performance
*   **NFR-1.1:** Sensor data acquisition and display updates MUST run in parallel and without noticeable delay.
*   **NFR-1.2:** The use of FreeRTOS MUST ensure efficient resource management.

### 4.2 Reliability
*   **NFR-2.1:** The system MUST operate without interruption over extended periods (weeks/months).
*   **NFR-2.2:** I2C communication errors SHOULD be handled robustly to prevent system crashes.
*   **NFR-2.3:** [v1.8.2, CHANGED v1.8.4] The system MUST detect when Wi-Fi is associated but no traffic gets through, and recover from it (detail of NFR-2.1). Every 60 s it checks for a sign of traffic: the MQTT client is connected (its keepalive proves round trips to the broker), the web server answered a request since the last check, or the default gateway answers at least one of 5 pings (2 s timeout each); the ping is only used when the other signs are missing. A check fails when Wi-Fi is associated and either has no IP address or shows no sign of traffic; 3 failed checks in a row force a Wi-Fi reconnection. The watchdog only acts after the gateway has answered ping at least once (until then it pings at every check), since some routers do not answer ping; while not associated, the usual reconnection (FR-5.5) applies. All values are in `main/config.h`. Before v1.8.4: "The system MUST detect when Wi-Fi is associated but no traffic gets through, and recover from it (detail of NFR-2.1). Every 60 s it pings the default gateway (3 pings). A check fails when Wi-Fi is associated and either has no IP address or the gateway does not answer; 3 failed checks in a row force a Wi-Fi reconnection. The watchdog only acts after the gateway has answered at least once, since some routers do not answer ping; while not associated, the usual reconnection (FR-5.5) applies. All values are in `main/config.h`." A router that occasionally ignored ping could then cause needless Wi-Fi reconnections while MQTT and the web page were working.
*   **NFR-2.4:** [v1.8.2, CHANGED v2.3.3, CHANGED v2.4.0, CHANGED v2.5.0, CHANGED v2.6.0] Since v2.6.0 `sys` also shows the source of the settings (`stored` or `menuconfig`, FR-12.1) and, in setup mode, the access point, its password, the connected devices and the last test (FR-12.3, FR-12.5) instead of the Wi-Fi link. Since v2.5.0 the sensor line of `sys` also shows the samples rejected since start (FR-1.6). Since v2.4.0 `sys` also shows the calibration of each sensor, the altitude with the sea-level factor, and the METAR check (FR-11.1, FR-11.2, FR-11.4). If the network is still down after 2 forced Wi-Fi reconnections, the system MUST restart; the history (FR-7.3) survives. To help diagnose such failures, the system logs the start reason at boot (power-on, software restart, watchdog, brownout...), logs a health line every 10 minutes (free heap, minimum free heap, largest free block, Wi-Fi signal, MQTT state, web requests served), and offers the console command `sys` with the uptime, start reason, [v2.0.0] device identifier, name, firmware version and sensor (FR-10.1 to FR-10.3), heap, Wi-Fi link, IP and gateway, watchdog state with the last sign of traffic and its source (since v1.8.4; before: last gateway reply), MQTT state and web requests served. [v2.3.3] The health line and `sys` also show the Wi-Fi connections lost since start, counted per disconnection reason, with the time since the last one, e.g. `Wi-Fi drops 3 (reason 6: 2, reason 200: 1), last 420 s ago`: comparing the count over a period with the web requests served shows whether drops follow the traffic. Failed reconnection attempts do not count; a forced reconnection does (reason 8). Five reasons are counted apart, any others together as `other`. The count starts at zero on every start.
*   **NFR-2.5:** [v2.6.0] The serial console MUST offer two commands to find where traffic between a device of the local network and the station is lost, without other tools on the network. Background: a phone reached the web page while a PC on the same network did not; the PC saw the station's MAC address as unreachable (its ARP requests got no answer), while the station kept working with the router and the broker.
    *   **`ping <ip> [count [size]]`:** the station pings any IPv4 address and prints each reply (bytes, sequence, TTL, time) or `no reply`, then the number sent, received and lost. Default 5 pings of 56 bytes, one per second, 1 s timeout; at most 100 pings and 1472 bytes (one 1500-byte frame), so large packets can be tested as with `ping -s 1400` on a PC (section 6.4). Values in `main/config.h`. It shows whether the path from the station to the device works.
    *   **`arp` / `arp clear`:** lists the ARP table of the station (IP address, MAC address, and the two-letter lwIP name of the interface, station or access point); `arp clear` empties it first. A device appears in the table when its ARP request for the station arrived (lwIP records the sender of a request for its own address) or after the station sent to it. So: `arp clear`, then try to reach the station from the device, then `arp`: when the device is listed, its packets reach the station and the answers are lost on the way back; when it is not, its packets never arrive. The table is read and cleared in the lwIP thread.
    *   Both commands also work in setup mode (FR-12.2), on the access point.

## 5. Technical Architecture (Summary)

## 6. Interfaces

### 6.1 User Interface (OLED)
*   Display of temperature, humidity, and air pressure. [v2.4.0] The values are calibrated (FR-11.1) and the pressure is reduced to sea level (FR-11.2).
*   Date and time in the header once the clock is synchronized.
*   Wi-Fi signal icon at the right edge of the header.
*   Measurement icon (filled dot) at the left edge of the header, shown for 0.5 s after each measurement.
*   [v1.8.0] The BOOT button switches the display off and on; the display switches off after 5 minutes without a button press by default (see FR-9.1, FR-9.2).

### 6.2 Hardware Interfaces
*   **I2C bus:** Uses GPIO 21 (SDA) and GPIO 22 (SCL) of the ESP32.
*   **BOOT button:** [v1.8.0] GPIO 0 (active low), read by interrupt after start-up to switch the display. Held during a reset, it still selects the download mode of the ESP32.
*   **Power supply:** 3.3V for the ESP32, BME280, and SSD1306.

### 6.3 Serial Interface
*   The serial interface is used for debug output at 115200 baud (ESP-IDF console UART, viewed with `idf.py monitor`).
*   [v1.6.0] Interactive console on the same UART (prompt `weather> `): `help`, `log info`, `log dump [N]`, `log clear` (see FR-7.4, FR-7.5).
*   [v1.8.0] Console commands `display on`, `display off`, `display status` (see FR-9.1).
*   [v1.8.2] Console command `sys`: system health (see NFR-2.4); [v2.0.0] also device, name, firmware and sensor (see FR-10.1 to FR-10.3).
*   [v2.4.0] Console command `cal`: `cal`, `cal set <temperature|humidity|pressure> <offset>`, `cal clear [channel]` (see FR-11.1). Each measurement line shows `Td=` and `QNH=` instead of the altitude estimate (see FR-11.2, FR-11.3).
*   [v2.6.0] Console command `setup`: `setup`, `setup cancel`, `setup show`, `setup clear` (see FR-12.6).
*   [v2.6.0] Console commands `ping <ip> [count [size]]`, `arp`, `arp clear` (see NFR-2.5).
*   [v2.0.0] `log dump` prints the columns `device_id,sensor_id,seq,time,temperature_c,humidity_rh,pressure_hpa`; `log info` also shows the history format, the device and the sensors (see FR-10.6).

### 6.4 Network Interface
*   **Wi-Fi:** 2.4 GHz station mode (WPA2-PSK, or an open network if no password is set).
*   **Wi-Fi:** [v1.2.0] Add a symbol to indicate WiFi connectivity in the yellow area (see FR-5.7).
*   **Wi-Fi power save:** [v1.8.4] Off by default (`WIFI_POWER_SAVE` in `main/config.h`). With modem power save on (the ESP-IDF default up to v1.8.3), the station stopped receiving with some routers while it could still send; turning it on saves energy, which matters for a battery supply (section 3.9).
*   **Wi-Fi access point and link:** [v1.8.7] The station scans all channels and joins the access point with the strongest signal (a mesh offers the same network from several nodes; before v1.8.7 it joined the first one found). Each association is logged with network name, access point (BSSID), channel, channel width (HT20/HT40), security and signal. ~~A-MPDU aggregation on reception is off by default (`sdkconfig.defaults`): the station receives little data, and a mesh access point kept tearing the Block Ack sessions down.~~ [CHANGED v1.8.8] A-MPDU aggregation is on in both directions (ESP-IDF default). v1.8.7 turned it off on reception because the `DELBA reason:37, initiator:0(recipient)` messages were misread: they came from the access point as recipient, so they concerned the station's transmission, and they are harmless. [CHANGED v2.3.2] A-MPDU aggregation is off when sending (`# CONFIG_ESP_WIFI_AMPDU_TX_ENABLED is not set` in `sdkconfig.defaults`) and stays on for reception. At about -68 dBm the link stalled for up to 5 s and then delivered the held packets at once: a `ping` from the local network lost 40 to 60 % and the replies after a stall arrived together, 5.2, 4.2, 3.2, 2.2 and 1.2 s late; the web page did not load in either browser. Without aggregation on sending, the loss fell to 0 to 10 % with short peaks of about 1 s. The `DELBA` messages of v1.8.7 already concerned the station's sending. The station sends little data, so the lower peak throughput when sending does not matter; the CSV download (FR-8.5) may take longer. If stalls come back, the setting can be turned on again with `idf.py menuconfig` (Component config → Wi-Fi). Opening and closing Block Ack sessions (`ba-add`, `ba-del`, `DELBA reason:39` after inactivity) is routine; since v1.8.8 these Wi-Fi driver messages are no longer logged (driver log level WARN, `main/config.h`), while the association line above still is. [v1.8.9] Each disconnection is logged with the network, access point (BSSID), signal and the reason with its meaning (for example `reason 2, access point did not answer authentication`), so a failing access point can be identified without the driver messages. A signal of about -60 dBm or better is needed for a responsive web page; at -65 to -75 dBm the link loses packets and answers can take seconds. [CHANGED v2.3.4] Low, stable rates: the station joins without 802.11n (`WIFI_PROTOCOLS`, 802.11b/g, in both directions) and sends every frame at a fixed 6 Mbps OFDM (`WIFI_TX_RATE`, `main/config.h`, set with the private ESP-IDF function `esp_wifi_internal_set_fix_rate`, which needs A-MPDU off when sending). Before v2.3.4 the driver chose the rate up to 802.11n: on channel 2 of a mesh, at -61 dBm and with no drops, the link passed small packets and lost large ones (ping loss to the station: 0 to 17 % with 56 bytes, 67 % with 300, 93 % with 700, 85 to 100 % with 1400; to the access point on the same path: 0 %), so MQTT and `/api/current` worked while `/api/charts` and the page stalled in every client. RSSI alone does not show this; `ping -s 1400` does. [CHANGED v2.6.0] The station joins with 802.11n again (`WIFI_PROTOCOLS` 802.11b/g/n), the most widely supported mode, and still sends every frame at the fixed 6 Mbps; the access point again chooses the rates at which it sends to the station. With 802.11b/g only, a PC on another node or band of a mesh could not reach the station while a phone could (its ARP requests got no answer); the `ping` and `arp` commands of NFR-2.5 find such cases. Should large packets to the station get lost again (`ping -s 1400` from a PC, or `ping <ip> 20 1400` from the station), `WIFI_PROTOCOLS` can be set back to 802.11b/g in `main/config.h`.
*   **DNS:** [v2.3.5] The station uses the DNS servers of the DHCP answer and, when these are missing or do not answer, the fallback server `8.8.8.8` (`CONFIG_LWIP_FALLBACK_DNS_SERVER_ADDRESS` in `sdkconfig.defaults`), which stays set across reconnections. ESP-IDF clears the DHCP servers on each DHCP start, and an answer without DNS servers leaves them empty until the next DHCP renewal. Before v2.3.5 the station could then not resolve the broker after an internet outage (`getaddrinfo() returns 202`, in the same millisecond as the attempt), while Wi-Fi, the gateway and the web page worked, so the network watchdog of NFR-2.3 saw nothing wrong and only a restart recovered MQTT. The cause was inferred from this behavior and the ESP-IDF code, not observed in the DHCP answer. The servers are logged with each IP address and shown by `sys`, e.g. `DNS: 192.168.0.1, backup none, fallback 8.8.8.8`.
*   **Setup mode:** [v2.6.0] Access point `ws-setup-<last 2 MAC bytes>` (WPA2-PSK, random password, channel 1, one client, address `192.168.4.1` with DHCP), a DNS server on UDP port 53 that answers every name with that address, and the setup page on TCP port 80; the station interface only scans and tests new credentials (see FR-12.3 to FR-12.5).
*   **NTP:** SNTP client (UDP port 123), default server `pool.ntp.org`.
*   **HTTPS client:** [v2.4.0] With a METAR airport configured, one request per hour (two at most) to `aviationweather.gov` (TCP 443, server certificate checked with the ESP-IDF certificate bundle), and the retained MQTT message `weather-station/<device_id>/metar` (see FR-11.4).
*   **MQTT:** [v1.5.0] Client publishing the weather data as JSON to the configured broker (TCP 1883 for `mqtt://`, 8883 for `mqtts://`), topic `weather-station/data` (see FR-6.1 to FR-6.6). [v1.8.4] Client ID `weather-station-` plus the last 3 bytes of the Wi-Fi MAC address (e.g. `weather-station-51a842`), shown when the client connects and by `sys`; before v1.8.4 the ESP-MQTT default `ESP32_` plus the same bytes. [CHANGED v2.0.0] Topics `weather-station/<device_id>/data` (readings) and `weather-station/<device_id>/info` (device, firmware, intervals, sensors; retained, sent on every connection and after a sensor change); the retained message on the former topic `weather-station/data` is cleared on every connection; client ID = device identifier (e.g. `ws-a0b76551a842`) (see FR-10.1, FR-10.4). [v2.1.0] Topic `weather-station/<device_id>/status`: `online` on connection, `offline` as last will (see FR-6.7). [v2.2.0] Data messages carry `rssi_dbm`, the lowest Wi-Fi RSSI since the previous message (see FR-5.8).
*   **HTTP:** [v1.7.0] Server on TCP port 80: `/`, `/api/current`, `/api/history?hours=N&points=P`, `/history.csv`, and `/favicon.ico` (empty answer, since v1.8.1) (see FR-8.1 to FR-8.6). [v2.0.0] `/api/info` (see FR-10.5). [v2.1.0] `/history.csv` gzip-compressed when the client accepts it (see FR-8.8). [v2.2.0] `/api/current` holds `rssi_dbm` (see FR-5.8). [v2.3.0] `/api/current` holds `firmware` and the heap figures (see FR-8.9). [v2.3.1] `/api/charts`: the three chart periods in one answer (see FR-8.4).

## 7. Open Issues / Future Extensions

*   **Hardware RTC:** Add an RTC module (e.g. DS3231) so the time of day survives power loss without Wi-Fi (the time of day via NTP is implemented in v1.1.0).
*   **QR code for setup:** In setup mode (FR-12.3), the display could show a QR code that joins the access point (`WIFI:T:WPA;S:<name>;P:<password>;;`) instead of the name and password; at 2 pixels per module a QR code of version 3 takes 58 × 58 pixels of the 128 × 64 display.
*   **Additional sensors:** Support a second sensor in the hardware and the drivers. The history format 2 (FR-10.6) and the identifiers (FR-10.3) already allow up to 254 sensors per station.
