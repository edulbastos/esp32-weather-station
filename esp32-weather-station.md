## 1. Introduction

### 1.1 Purpose of the Document
This document describes the functional and non-functional requirements for the ESP32 Weather Station. It serves as a reference for the development, validation, and future extensions of the system.

### 1.2 Scope
The specification covers the acquisition of temperature, humidity, and air pressure data using a BME280 sensor, the display of this data on an SSD1306 OLED display, and the underlying software architecture based on FreeRTOS.

### 1.3 Target Audience
This document is intended for developers, testers, and anyone interested in gaining an in-depth understanding of the weather station.

## 2. Product Overview

### 2.1 Brief Description
The ESP32 Weather Station is a standalone device that continuously collects environmental data (temperature, humidity, air pressure) and displays it in real time on a small OLED screen. The system is robust, energy-efficient, and takes advantage of a real-time operating system (FreeRTOS) for reliable and responsive performance.

### 2.2 Goals and Vision
The main goal is to provide a weather station that is easy to build and use, delivers accurate measurements, and can serve as a foundation for further IoT projects.

## 3. Functional Requirements

### 3.1 Sensor Data Acquisition
*   **FR-1.1:** The system MUST acquire temperature readings from the BME280 sensor.
*   **FR-1.2:** The system MUST acquire humidity readings from the BME280 sensor.
*   **FR-1.3:** The system MUST acquire air pressure readings from the BME280 sensor.
*   **FR-1.4:** [CHANGED v1.4.0] The sensor data MUST be updated at the measurement interval set in sdkconfig (FR-3.2), 2 seconds by default. Before v1.4.0: "at least every 2 seconds".
*   **FR-1.5:** The system MUST provide a means to safely synchronize access to the I2C bus between different tasks (FreeRTOS mutex `i2cMutex`).

### 3.2 Data Display on OLED
*   **FR-2.1:** The system MUST display the current temperature on the SSD1306 OLED display.
*   **FR-2.2:** The system MUST display the current humidity on the SSD1306 OLED display.
*   **FR-2.3:** The system MUST display the current air pressure on the SSD1306 OLED display.
*   **FR-2.4:** The OLED display MUST be refreshed at least once every second.
*   **FR-2.5:** The displayed values MUST be clearly legible and include the corresponding units (e.g. °C, %RH, hPa).
*   **FR-2.6:** [v1.3.0] The system MUST display an icon to indicate when a measurement arrives and disappear after 0.5s. The icon is a filled dot at the left edge of the OLED header; the display is redrawn as soon as a new measurement arrives. The duration is set in `main/config.h`.

### 3.3 Configuration
*   **FR-3.1:** Configuration parameters such as display dimensions, I2C pins and addresses of the sensors and displays, and sea-level pressure MUST be defined centrally in a dedicated header file (`main/config.h`).
*   **FR-3.2:** [v1.4.0] Measurement interval time MUST be done in sdkconfig. It is set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_MEASURE_PERIOD_S`), in seconds, from 1 to 3600, default 2; `main/config.h` takes the value from there.

### 3.4 Error Handling
*   **FR-4.1:** The system MUST output an error message on the serial console (via `ESP_LOGE`) if the OLED display cannot be initialized.
*   **FR-4.2:** The system MUST output an error message on the serial console (via `ESP_LOGE`) if the BME280 sensor cannot be initialized.
*   **FR-4.3:** In the event of a critical initialization error (display or sensor), the system MUST remain in an error mode or stop operating.

### 3.5 Time of Day
*   **FR-5.1** [v1.1.0]: The system MUST obtain the current date and time from an NTP server (default `pool.ntp.org`) over Wi-Fi (station mode) and keep the clock synchronized periodically.
*   **FR-5.2** [v1.1.0]: The local time MUST use the time zone defined in `main/config.h` (default: UTC-3, Brasília, without daylight saving time).
*   **FR-5.3** [v1.1.0]: Once the clock is synchronized, the OLED header MUST show the date and time as `DD/MM/YYYY HH:MM`. Before synchronization, the header shows the title "WEATHER STATION". A sensor error ("SENSOR ERROR") takes precedence over the date and time.
*   **FR-5.4** [v1.1.0]: Once the clock is synchronized, every measurement written to the serial console MUST be prefixed with a timestamp in the format `YYYY-MM-DD HH:MM:SS`.
*   **FR-5.5** [v1.1.0]: Wi-Fi or NTP failures MUST NOT be critical errors: the weather station MUST keep measuring and displaying, log a warning (`ESP_LOGW`), and retry the Wi-Fi connection periodically (every 10 s by default).
*   **FR-5.6** [v1.1.0]: The Wi-Fi credentials (SSID and password) MUST be set via `idf.py menuconfig` ("Weather Station" menu) and stored only in the local `sdkconfig`, which is not version-controlled. With an empty SSID, Wi-Fi and the time of day are disabled.
*   **FR-5.7** [v1.2.0]: The OLED header MUST show a Wi-Fi icon at its right edge: 1 to 3 arcs according to the signal strength (3 arcs at RSSI ≥ -60 dBm, 2 arcs at ≥ -70 dBm, 1 arc below; thresholds in `main/config.h`) while connected, and an X while disconnected. With no SSID configured, no icon is shown. The header text is centered in the space left of the icon.
*   **FR-5.8** [v2.2.0]: The station MUST report the Wi-Fi signal strength (RSSI of the access point, in dBm) with its data, so the quality of the link at its location can be followed over time and correlated with failures.
    *   The RSSI is sampled with every measurement (FR-3.2) while Wi-Fi is connected.
    *   **MQTT:** each data message (FR-6.3, FR-10.4) adds `rssi_dbm`, an integer: the lowest RSSI sampled since the previous message, so short drops of the signal between two publishes are not hidden. The field is left out when no sample was taken in the interval. Example: `{"device_id":"ws-a0b76551a842","sensor_id":"bme280-3fa91c07","time":1792161125,"temperature_c":23.41,"humidity_rh":56.12,"pressure_hpa":1012.84,"rssi_dbm":-67}`. The RSSI belongs to the station, not to a sensor: it is not a sensor channel (FR-10.3) and is not listed in the info message.
    *   **Web:** `/api/current` (FR-8.3) adds `rssi_dbm`, the current RSSI, `null` while Wi-Fi is not connected. The page (FR-8.2) shows it in dBm, e.g. `-67 dBm`, on a line of its own below the status line; both lines are aligned to the right, so the Wi-Fi signal bars at the end of the status line stand at the right edge, with the RSSI below them. This helps when placing the station.
    *   The RSSI is **not** stored in the measurement history (FR-7.1, FR-10.6): the record format, `log dump`, `/history.csv` and the web charts stay unchanged. The record has no free byte, and storing the RSSI would need a new history format; long-term series of the RSSI are left to the MQTT consumers.
    *   Changes FR-6.3, FR-8.2 and FR-8.3.

### 3.6 Data Transmission (MQTT)
*   **FR-6.1** [v1.5.0]: The system MUST transmit the weather data over Wi-Fi to an MQTT broker (MQTT 3.1.1; `mqtt://` or `mqtts://` URI). This implements the "Wi-Fi connectivity" extension proposed in section 7 up to v1.4.0.
*   **FR-6.2** [v1.5.0]: The latest valid measurement MUST be published at the publish interval set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_MQTT_PUBLISH_PERIOD_S`), in seconds, from 1 to 86400, default 60. The interval is independent of the measurement interval (FR-3.2). A measurement that was already published is not sent again, and nothing is sent while the sensor has no valid reading.
*   **FR-6.3** [v1.5.0, CHANGED v2.0.0, CHANGED v2.2.0]: Since v2.2.0 each message also carries `rssi_dbm`, the lowest Wi-Fi RSSI since the previous message (FR-5.8). Since v2.0.0 each message also carries `device_id` and `sensor_id` (FR-10.4). Before v2.0.0: Each message MUST be a JSON object with the fields `temperature_c`, `humidity_rh` and `pressure_hpa` (two decimal places) and, once the clock is synchronized (FR-5.1), `time` with the Unix time of the measurement in seconds. Example: `{"time":1792161125,"temperature_c":23.41,"humidity_rh":56.12,"pressure_hpa":1012.84}`.
*   **FR-6.4** [v1.5.0, CHANGED v1.8.8, CHANGED v2.0.0]: Since v2.0.0 messages go to the topic of the station, `weather-station/<device_id>/data` (prefix in `main/config.h`), and the station publishes an info message (FR-10.4); QoS and retain flag are unchanged. Before v2.0.0: Messages MUST be published to the topic defined in `main/config.h` (default `weather-station/data`) with QoS 1 and the retain flag set, so a new subscriber receives the latest reading at once. With QoS 1 the broker confirms each message, and a message not yet confirmed when the connection drops is sent again after the reconnection (messages older than 30 s are dropped; the flash history keeps every reading). Before v1.8.8: QoS 0, so a reading in transit when the connection dropped was lost for MQTT.
*   **FR-6.5** [CHANGED v1.7.1, CHANGED v1.8.7, CHANGED v1.8.8, CHANGED v2.0.1]: MQTT failures MUST NOT be critical errors: the weather station MUST keep measuring and displaying, log a warning (`ESP_LOGW`), skip the publish while disconnected, and reconnect to the broker automatically. While Wi-Fi has an IP address, a failed connection is retried every 10 s by default; while Wi-Fi is down, no connection is attempted; when Wi-Fi gets an IP address again, the client reconnects at once. Since v1.8.7 the MQTT keepalive is 30 s (`main/config.h`), so a connection that stops delivering is noticed after about 45 s; before, the ESP-MQTT default of 120 s took up to 3 minutes. Since v1.8.8 the keepalive is 60 s: a dead connection is noticed after about 90 s, and stalls of up to about 30 s (seen on the path to the broker) no longer force a reconnection, as they did with 30 s. Since v2.0.1 a send to the broker may wait up to 30 s for the link (`MQTT_NETWORK_TIMEOUT_MS` in `main/config.h`) before the connection is dropped; before, the ESP-MQTT default of 10 s dropped the connection when a stall of the link (seen at about -65 dBm) hit the resend of an unconfirmed message (`Writing didn't complete in specified timeout`). Before v1.7.1: "reconnect to the broker automatically (every 10 s by default)", which also tried, and logged errors, while Wi-Fi was down, and waited up to 10 s after Wi-Fi returned.
*   **FR-6.6** [v1.5.0]: The broker URI, user name and password MUST be set via `idf.py menuconfig` ("Weather Station" menu) and stored only in the local `sdkconfig`, which is not version-controlled. With an empty broker URI, or without Wi-Fi (FR-5.6), data transmission is disabled.
*   **FR-6.7** [v2.1.0]: The station MUST publish its online status to `weather-station/<device_id>/status` (QoS 1, retained): `online` on every connection to the broker, and `offline` as its MQTT last will, which the broker publishes when the connection drops or the station stops answering (after about 1.5 keepalive periods, 90 s with the keepalive of FR-6.5). A management system sees at once which stations are reachable by subscribing to `weather-station/+/status`. The payloads are defined in `main/config.h`. This implements the "Online status" extension proposed in section 7 up to v2.0.1.

### 3.7 Measurement History
*   **FR-7.1** [v1.6.0]: The system MUST store a history of the measurements in the internal flash, in the 5 MB data partition `history` defined in `partitions.csv`. This implements the "Data logging" extension proposed in section 7 up to v1.5.0 (internal flash option; no SD card). The partition table keeps the offsets of `nvs` and `phy_init` and enlarges the app partition from 1 MB to 2 MB.
*   **FR-7.2** [v1.6.0]: The latest valid measurement MUST be stored at the log interval set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_LOG_PERIOD_S`), in seconds, from 1 to 86400, default 60. The interval is independent of the measurement and publish intervals. A measurement is stored only once, and nothing is stored while the sensor has no valid reading.
*   **FR-7.3** [v1.6.0, CHANGED v2.0.0]: Since v2.0.0 the records are in format 2 (FR-10.6): each sector names the device and the sensors, and each measurement its sensor; capacity 325,120 measurements, about 7.4 months at 60 s. Before v2.0.0: Each record MUST hold a sequence number, the Unix time of the measurement (0 before the clock is synchronized), the temperature (0.01 °C), the humidity (0.01 %RH), the pressure (0.1 hPa) and a CRC16. The history works as a ring buffer: when it is full, the oldest 4 KB sector (256 records) is erased. Capacity: 327,680 records, about 7.5 months at 60 s. The history survives restarts and power loss; a record cut short by a power loss is discarded.
*   **FR-7.4** [v1.6.0, CHANGED v2.0.0]: Since v2.0.0 the CSV columns are `device_id,sensor_id,seq,time,temperature_c,humidity_rh,pressure_hpa`, and `log info` also shows the format version, the device and the sensors (FR-10.6). Before v2.0.0: The history MUST be readable on the serial console (prompt `weather> `, 115200 baud): `log info` shows the number of records and the space used; `log dump [N]` prints the last N records (all if N is omitted), oldest first, as CSV with the columns `seq,time,temperature_c,humidity_rh,pressure_hpa`, where `time` is local time `YYYY-MM-DD HH:MM:SS` (empty if unknown). Other log output is suppressed during the dump. `help` lists the commands.
*   **FR-7.5** [v1.6.0]: The command `log clear` MUST erase the whole history.
*   **FR-7.6** [v1.6.0]: History failures MUST NOT be critical errors: if the partition is missing or a write fails, the system logs a warning (`ESP_LOGW`) and keeps measuring, displaying and publishing.

### 3.8 Web Page
*   **FR-8.1** [v1.7.0]: The system MUST serve a web page on the local network over HTTP (port 80), reached by the IP address of the station. The server starts once Wi-Fi has an IP address, and the URL (`Web page at http://<ip>/`) is logged on the serial console on every connection. There is no name resolution (mDNS) and no password: the page is read-only and offers no action that changes the station. This implements the "Web server" extension proposed in section 7 up to v1.6.0.
*   **FR-8.2** [v1.7.0, CHANGED v1.8.1, CHANGED v1.8.6, CHANGED v2.2.0]: Since v2.2.0 the status line is aligned to the right, and a second line below it shows the Wi-Fi RSSI in dBm, e.g. `-67 dBm` (FR-5.8). The page (`/`) MUST show the current temperature, humidity and pressure, the time of the measurement and the Wi-Fi signal level, refreshed at the measurement interval (at least every 1 s). It MUST work without internet access (no external files) and adapt to phone screens and to the light/dark setting of the browser. Since v1.8.1 the page carries its own tab icon (embedded SVG), and `/favicon.ico` answers `204 No Content`, so browsers no longer cause a 404 warning on the serial console; before v1.8.1 the page had no icon and `/favicon.ico` answered 404. Since v1.8.6 the home-screen icons that Safari on iOS asks for (`/apple-touch-icon.png`, `/apple-touch-icon-precomposed.png`) get the same empty answer, and the page is sent gzip-compressed (about 5 KB instead of 12.5 KB) to browsers that accept it, uncompressed to the others.
*   **FR-8.3** [v1.7.0, CHANGED v2.0.0, CHANGED v2.2.0, CHANGED v2.3.0]: Since v2.3.0 the answer also holds `firmware`, `heap_free_kb`, `heap_min_kb` and `heap_largest_kb` (FR-8.9). Since v2.2.0 the answer also holds `rssi_dbm`, the current Wi-Fi RSSI in dBm, `null` while Wi-Fi is not connected (FR-5.8). Since v2.0.0 the answer also holds `device_id`, `name` and `sensor_id`, and `/api/info` returns the info message (FR-10.5). Before v2.0.0: `/api/current` MUST return the current values as JSON: `valid`, `time` (Unix time of the measurement, `null` before NTP sync), `age_s`, `temperature_c`, `humidity_rh`, `pressure_hpa`, `wifi_level` (FR-5.7), `measure_period_s` and `log_period_s`. With `valid` false, the measurement fields are left out.
*   **FR-8.4** [v1.7.0, CHANGED v1.8.3, CHANGED v1.8.5, CHANGED v1.8.7, CHANGED v1.8.9, CHANGED v2.3.1, CHANGED v2.3.2]: Since v2.3.1 the page loads the three periods with one request, `/api/charts`, which returns `{"periods":[...]}` with one object per period in the format of `/api/history` (from RAM); a request that gets no answer within 20 s is retried after 5 s as before. Each new connection costs a TCP handshake and a request that can be lost; with about 20 % packet loss at -70 dBm the three requests of v1.8.9 to v2.3.0, made one after the other, often each waited for a retransmission, and the charts of a new page on an iPhone (whose Wi-Fi power saving adds up to 150 ms per round trip) stayed at "Loading…" for many seconds. `/api/history` is unchanged. The page MUST show charts of temperature, humidity and pressure from the measurement history (FR-7.1), over a period chosen with buttons: 1 hour, 24 hours (default) or 7 days; the choice is remembered by the browser. The data come from `/api/history?hours=N&points=P` (N from 1 to 8760, default 24; P from 10 to 1440, default 150, `main/config.h`) as JSON: `hours`, `points`, `bucket_s`, `log_period_s`, `available` and `records`, a list of `[time, temperature_c, humidity_rh, pressure_hpa]`. The station divides the period into P intervals of `bucket_s` seconds and sends the average of the records in each interval (one point per record when the interval is shorter than the log interval); records without a time are left out. The page loads this data when it opens, when the period changes, every 30 minutes, and (since v1.8.5) when it becomes visible again or when the next measurement shows that measurements were missed (more than twice the measurement or log interval, plus 10 s, since the last one; at most once a minute) — browsers slow down or freeze hidden pages, and before v1.8.5 the new point was then drawn after a gap until the page was reloaded by hand; in between it adds each new measurement from `/api/current` to the charts, averaged into the last point while that point is younger than one interval, so the number of points stays about P. A pause longer than three intervals (or three log intervals) breaks the line. Since v1.8.7, when the period changes the charts are cleared at once and show "Loading…" until the data arrive, and a history request that gets no answer within 20 s is given up and retried after 5 s ("station slow to answer, retrying…"); before, the charts of the previous period stayed until the answer came, which on a weak link could take half a minute. Since v1.8.9 the station keeps, for each of the three periods, a table of 150 time buckets in RAM (24 s, 9.6 min and 67.2 min per bucket) holding the running averages of the measurements; every measurement updates one bucket per table, the tables are rebuilt from the flash history at start-up, and `/api/history` answers these periods from RAM in constant time, without reading the flash, whatever the measurement or log interval (the JSON adds `measure_period_s` and `source`: `measurements`; other values of `hours` or `points` are still averaged from the flash history, `source`: `history`). Because the tables are fed by the measurements, short periods can be more detailed than the log interval. The page loads all three periods when it opens (the selected one first) and adds each new measurement to all of them, so switching between periods is instant; before v1.8.9 each switch requested the period from the station and the answer read the flash history. Before v1.8.3: "The page MUST show charts of temperature, humidity and pressure over the last 24 hours (`main/config.h`), taken from the measurement history (FR-7.1) and refreshed at the log interval (at least every 10 s). A pause longer than three log intervals breaks the line. The data come from `/api/history?hours=N` (N from 1 to 8760, default 24) as JSON: `hours`, `log_period_s`, `available` and `records`, a list of `[time, temperature_c, humidity_rh, pressure_hpa]`; at most 1440 records, evenly thinned out; records without a time are left out." (the whole 24-hour data, thinned by skipping records, was loaded again at every log interval).
    *   [v2.3.2] The number of chart points MUST depend on the period, so the chart data of a new page fit in fewer TCP segments: 60 points for 1 hour (1 minute each), 96 for 24 hours (15 minutes each) and 84 for 7 days (2 hours each), 240 in all instead of 3 × 150 = 450 (`main/config.h`). A full `/api/charts` answer shrinks from about 14 KB (10 segments) to about 7.5 KB (6 segments); on a link that loses packets in bursts, each segment less is one chance less to wait for a retransmission (FR-8.6). The resolution stays above what the weather changes in each period and what a chart of 330 to 900 pixels shows (one point per 4 to 15 pixels). The tables in RAM (FR-8.4 since v1.8.9) keep these numbers of buckets; `/api/history` without `points` uses the number of the period for 1, 24 and 168 hours (served from RAM), and 150 for other periods as before. The JSON format is unchanged.
*   **FR-8.5** [v1.7.0, CHANGED v2.0.0]: Since v2.0.0 the file is named `history-<device_id>.csv` (before: `weather-history.csv`) and has the columns of FR-10.6. Before v2.0.0: `/history.csv` MUST download the whole history as a CSV file, in the format of `log dump` (FR-7.4). The server handles one request at a time, so other requests wait while the download runs.
*   **FR-8.6** [v1.7.0, CHANGED v1.8.1, CHANGED v1.8.6, CHANGED v1.9.1, CHANGED v2.0.1, CHANGED v2.1.1, CHANGED v2.3.1]: Since v2.3.1 the station composes each answer itself (status line, headers and body in one buffer of 4 KB plus headers, `main/config.h`) and sends it with one write per buffer: an answer that fits goes out with `Content-Length` in a single write, a longer one chunked, one chunk per write. ESP-IDF's response functions write every header field, separator and line break separately, and with `TCP_NODELAY` each write became a packet: `/api/current` took about 11 packets before v2.3.1, the chunks of 1 KB three packets each; on a lossy link every packet is a chance to wait for a retransmission. Since v2.3.1 an answer that takes 1 s or more (`WEB_SLOW_ANSWER_MS`), counted from the opening of its connection until its last byte is handed to TCP, is logged as a warning with the address, the size and the time, e.g. `Slow answer: /api/charts, 16384 bytes in 3.2 s`; lost handshake or request segments show up in it, a slow delivery only for answers larger than the TCP send buffer (11.5 KB). The web page MUST NOT be critical: it needs Wi-Fi (FR-5.6) and is disabled without an SSID; server failures only log a warning (`ESP_LOGW`). At most 4 connections are open at once; a new client closes the least recently used one. Since v1.8.1 the server answers one request per connection (`Connection: close`) and then closes it, so idle connections kept open by browsers are not reset later; before v1.8.1 connections stayed open and each browser reset logged `error in recv : 104`. Since v1.8.6 the server waits up to 15 s (`main/config.h`) for the network to take more data before it gives up an answer; before, it gave up after 5 s, which on a lossy Wi-Fi link cut pages off halfway. The history answer reads only the flash sectors that can hold the requested period, so it starts within a fraction of a second (before v1.8.6 it probed every sector of the partition first, about 1.5 s). Since v1.9.1 the server sends without Nagle's algorithm (`TCP_NODELAY` on every connection): ESP-IDF writes each response header and each chunk in several small pieces, and before v1.9.1 every piece after the first waited for the browser's delayed ACK (up to 200 ms), so each request took about 0.2 to 0.35 s even for a few hundred bytes and a new page with its four data requests about 1.5 s. Since v2.0.1 the CSV download (FR-8.5) turns Nagle's algorithm back on for its connection and is sent in chunks of 4 KB (other answers: 1 KB), and the TCP send buffer holds 8 segments instead of 4 (`CONFIG_LWIP_TCP_SND_BUF_DEFAULT=11520` in `sdkconfig.defaults`). ESP-IDF sends every chunk in three pieces (size line, data, line break); with `TCP_NODELAY` each piece left as a packet of its own, so from v1.9.1 to v2.0.0 a long download sent three packets per kilobyte, two of them a few bytes long, and on a link at about -65 dBm it stalled until the 15 s send timeout aborted it (`error in send : 11`); the other requests of an open page, queued behind the download, then failed as well (`error in send : 104`). Since v2.1.1 a connection whose answer failed (the client stopped taking data) is closed with a reset (`SO_LINGER` with a time of 0), which drops its unsent data at once; other connections close normally, without waiting for the client's acknowledgment (waiting, as a linger time on every close would, blocks the server for the delayed ACK of each request, which made the page noticeably slower on an iPhone). lwIP gives up a connection after 6 retransmissions instead of 12 (`CONFIG_LWIP_TCP_MAXRTX=6` in `sdkconfig.defaults`), a few minutes instead of over 10. Before v2.1.1 the limit of 4 connections covered only open ones: after the server closed a connection (after the answer, after a failed send, or for a new client), lwIP kept retransmitting its unacknowledged data, up to 11.5 KB each, for over 10 minutes. On a stalled link at about -65 dBm, with a page open that kept making requests, these connections used up the heap (13 KB free, largest block 1 KB): MQTT could no longer connect (`Software caused connection abort`), the watchdog ping task could not be created, and the network was only recovered by the forced Wi-Fi reconnection of NFR-2.3.
*   **FR-8.7** [v1.9.0]: The charts of the web page MUST show the values of their points on demand, with a cursor shared by the three charts. With a mouse, pointing at any chart places the cursor at the chart point closest in time to the pointer and shows, in each of the three charts, a vertical line at that time, a dot on the line and a label with the value (one decimal, with unit) and the time of the point (HH:MM:SS for 1 hour, HH:MM for 24 hours, day, month and HH:MM for 7 days); the cursor disappears when the pointer leaves the chart. On a touch screen, touching a chart or sliding a finger along it places the cursor the same way; it stays after the finger lifts and disappears when the page is touched outside the charts; vertical swipes over a chart still scroll the page. The cursor follows new measurements without disappearing, is hidden inside a break of the line (FR-8.4) and when the period changes. Each point is the average of its time bucket (FR-8.4), as stated below the charts. The values come from the chart data already loaded by the page; the station is not asked for anything more.
*   **FR-8.8** [v2.1.0]: `/history.csv` MUST be sent gzip-compressed (`Content-Encoding: gzip`) to clients that accept it (`Accept-Encoding: gzip`), and uncompressed to the others; browsers decompress it on the fly and save the plain CSV. The station compresses while it reads the history, so no copy of the file is kept. The compressor is a compact deflate encoder of its own (4 KB window, fixed Huffman codes, about 16 KB of RAM during the download); the miniz compressor of the ESP32 ROM needs about 300 KB of RAM, more than the station has free. The CSV becomes about 5 times smaller (a full history of about 25 MB about 5.3 MB). Without memory for the compressor the file is sent uncompressed. This implements the "Compressed CSV download" extension proposed in section 7 up to v2.0.1.
*   **FR-8.9** [v2.3.0]: The web page MUST show the firmware version and the heap memory of the station, so a problem can be diagnosed without the serial console (`sys`, NFR-2.4).
    *   `/api/current` (FR-8.3) adds `firmware` (the version of FR-10.4, e.g. `v2.3.0`) and the heap of 8-bit capable memory in KB, as `sys` shows it: `heap_free_kb` (free now), `heap_min_kb` (lowest free since the start) and `heap_largest_kb` (largest free block). The lowest value shows a shortage that has passed; the largest block shows fragmentation, which can make allocations fail while enough memory is free in total (as in the incident of FR-8.6 before v2.1.1: 13 KB free, largest block 1 KB).
    *   The page shows them on the first line of its footer, aligned to the right, opposite the CSV download link (on a narrow screen they move to a line of their own, still on the right), refreshed with every answer of `/api/current`, e.g. `firmware v2.3.0 · heap 142 KB free (min 98 KB, largest block 64 KB)`. The line is empty while the station cannot be reached.
    *   Changes FR-8.3.

### 3.9 Energy Saving
This section gathers the requirements that reduce the power consumption, in view of a future battery supply.

*   **FR-9.1** [v1.8.0]: The user MUST be able to switch the OLED display off and on: the BOOT button of the board (GPIO0) toggles it, and the serial console offers `display on`, `display off` and `display status`. When off, the panel is in sleep mode (SSD1306 command `0xAE`) and no frame is sent over I2C; measuring, history, MQTT and the web page continue. When switched on, the panel shows the current data at once. The display is on after every start-up.
*   **FR-9.2** [v1.8.0]: The display MUST switch itself off after a period without user interaction (a button press or a `display` command), set via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_DISPLAY_TIMEOUT_MIN`), in minutes, from 0 to 1440, default 5; 0 disables the automatic switch-off. A button press switches it on again and restarts the period. Each switch is logged on the serial console with its cause (button, console or inactivity).

### 3.10 Identification
This section gives every station, every sensor and every measurement an identifier, so a management system can tell stations and sensors apart and keep the data of several stations together. It breaks compatibility with v1.x in two places: the MQTT topic (FR-10.4) and the history format (FR-10.6); the requirements it changes are named in each item and marked `[CHANGED v2.0.0]`.

*   **FR-10.1** [v2.0.0]: Each station MUST have a unique, permanent device identifier derived from the factory base MAC address in eFuse (the Wi-Fi station MAC): `ws-` followed by all 6 bytes in lowercase hex, e.g. `ws-a0b76551a842`. It does not change with firmware updates, reflashing, erasing NVS or changing the Wi-Fi settings. It is logged at boot and shown by `sys` (NFR-2.4). The MQTT client ID becomes the device identifier (section 6.4; before: `weather-station-` plus the last 3 bytes of the MAC address).
*   **FR-10.2** [v2.0.0]: The user MAY give the station a free-text name (e.g. "Varanda") via `idf.py menuconfig` ("Weather Station" menu, `CONFIG_WS_DEVICE_NAME`, up to 32 characters, default empty). The name is for people only and is never used as a key; it is shown by `sys`, in the MQTT info message (FR-10.4) and on the web page (FR-10.5).
*   **FR-10.3** [v2.0.0]: Each sensor MUST have an identifier that tells physical chips apart: its type followed by the CRC-32 (IEEE 802.3) in lowercase hex of its factory trimming parameters, e.g. `bme280-3fa91c07`. For the BME280 these are `dig_T1` to `dig_H6` (32 bytes: registers `0x88`–`0x9F`, `0xA1` and `0xE1`–`0xE7`), which the driver already reads at initialization. The BME280 has no serial number; the trimming parameters differ from chip to chip, but the manufacturer does not guarantee that they are unique. Each sensor also has a position: its index in the station configuration (`main/config.h`, 0 for the BME280) and its bus address (`i2c@0x76`); the position names the measuring point, the identifier the chip. Each quantity a sensor measures is a channel with a fixed identifier (`temperature`, `humidity`, `pressure`). The full identifier of a channel is `<device_id>/<sensor_id>/<channel>`, e.g. `ws-a0b76551a842/bme280-3fa91c07/temperature`.
*   **FR-10.4** [v2.0.0]: MQTT messages MUST be published per station. Changes FR-6.3 and FR-6.4.
    *   Data messages go to `weather-station/<device_id>/data` (prefix `weather-station` in `main/config.h`), with QoS 1 and the retain flag as before, and carry `device_id` and `sensor_id` in addition to the fields of FR-6.3. Example: `{"device_id":"ws-a0b76551a842","sensor_id":"bme280-3fa91c07","time":1792161125,"temperature_c":23.41,"humidity_rh":56.12,"pressure_hpa":1012.84}`. With several stations on one broker, each keeps its own retained reading; before v2.0.0 all stations published to `weather-station/data` and overwrote each other's retained message.
    *   On every connection, and after a sensor change (FR-10.7), the station publishes a retained message (QoS 1) to `weather-station/<device_id>/info` with `device_id`, `name`, `firmware` (version), `measure_period_s`, `publish_period_s`, `log_period_s` and `sensors`, a list with, per sensor, `id`, `type`, `index`, `address` and `channels`, a list with, per channel, `id`, `unit` and `resolution`. A management system finds every station and its sensors by subscribing to `weather-station/+/info`.
    *   On every connection the station also clears the retained message on the former topic `weather-station/data` (empty retained message), so subscribers of that topic do not keep receiving a stale reading.
*   **FR-10.5** [v2.0.0]: The web interface MUST show and serve the identifiers. Changes FR-8.3 and FR-8.5.
    *   `/api/current` adds `device_id`, `name` and `sensor_id`.
    *   A new endpoint `/api/info` returns the same JSON as the MQTT info message (FR-10.4).
    *   The page shows the name, or the device identifier when no name is set, in its title and its footer, and the device and sensor identifiers in the footer.
    *   `/history.csv` is downloaded as `history-<device_id>.csv`, in the format of FR-10.6.
    *   The charts (FR-8.4) show the sensor at position 0, whatever chip is installed; a sensor change does not break the line.
*   **FR-10.6** [v2.0.0]: The history MUST record the device and the sensor of every measurement, in a new format (format 2) that replaces the one of FR-7.3. Changes FR-7.3, FR-7.4 and FR-8.5.
    *   Records stay 16 bytes, 256 per 4 KB sector, with a CRC16 over the first 14 bytes. Every record starts with a 24-bit sequence number (compared modulo 2^24; it restarts at 0 after 16,777,216 records, far more than the history holds) and a type byte: the sensor index (0 to 253) for a measurement, `0xFE` for a control record; `0xFF` is never used, as in erased flash.
    *   **Measurement record:** sequence number, sensor index (0 to 253), Unix time of the measurement (0 before the clock is synchronized), three 16-bit channel values whose meaning and scale come from the sensor type (BME280: temperature 0.01 °C, humidity 0.01 %RH, pressure 0.1 hPa), CRC16.
    *   **Control record** (type byte `0xFE`): sequence number, `0xFE`, kind, 9 bytes of data, CRC16. Kind 1, **sector header**: format version and device identifier (6 bytes). Kind 2, **sensor definition**: sensor index, sensor type, bus address and the 4-byte fingerprint of FR-10.3.
    *   The first record of every sector is a sector header, followed by one sensor definition per connected sensor. When a sensor changes (FR-10.7), a new definition for its index is written before its next measurement, in the middle of the sector; a reader keeps the latest definition per index while it reads a sector. Every sector therefore describes itself, also after the ring buffer has erased older sectors.
    *   With one sensor, 2 records per sector are control records: capacity 325,120 measurements, about 7.4 months at 60 s (before: 327,680).
    *   `log dump` and `/history.csv` print the columns `device_id,sensor_id,seq,time,temperature_c,humidity_rh,pressure_hpa` (before: `seq,time,temperature_c,humidity_rh,pressure_hpa`). The two new columns add about 32 bytes per line; a full history grows from about 16 MB to about 27 MB of CSV.
    *   `log info` also shows the format version, the device identifier and the sensors defined in the history.
    *   **No compatibility with v1.x:** a sector whose first record is a valid record but not a format 2 header holds data of the format before v2.0.0. Such sectors are ignored (not read, not counted) and erased when the ring buffer reaches them, or by `log clear`; at start-up their number is logged as a warning (`ESP_LOGW`). Erasing them all at once would delay the start by up to a minute. The history of a v1.x station MUST be downloaded (`/history.csv`) before updating. A firmware before v2.0.0 cannot read format 2; going back requires `log clear`.
*   **FR-10.7** [v2.0.0]: The station MUST detect a sensor replacement. At start-up and on every re-initialization of a sensor (after I2C errors), it compares the sensor identifier with the last one stored in NVS for that position. On a change it logs a warning (`ESP_LOGW`, position, old and new identifier), stores the new identifier, writes a new sensor definition to the history (FR-10.6) and publishes the MQTT info message again (FR-10.4). The first identifier seen at a position is stored without a warning.

## 4. Non-Functional Requirements

### 4.1 Performance
*   **NFR-1.1:** Sensor data acquisition and display updates MUST run in parallel and without noticeable delay.
*   **NFR-1.2:** The use of FreeRTOS MUST ensure efficient resource management.

### 4.2 Reliability
*   **NFR-2.1:** The system MUST operate without interruption over extended periods (weeks/months).
*   **NFR-2.2:** I2C communication errors SHOULD be handled robustly to prevent system crashes.
*   **NFR-2.3:** [v1.8.2, CHANGED v1.8.4] The system MUST detect when Wi-Fi is associated but no traffic gets through, and recover from it (detail of NFR-2.1). Every 60 s it checks for a sign of traffic: the MQTT client is connected (its keepalive proves round trips to the broker), the web server answered a request since the last check, or the default gateway answers at least one of 5 pings (2 s timeout each); the ping is only used when the other signs are missing. A check fails when Wi-Fi is associated and either has no IP address or shows no sign of traffic; 3 failed checks in a row force a Wi-Fi reconnection. The watchdog only acts after the gateway has answered ping at least once (until then it pings at every check), since some routers do not answer ping; while not associated, the usual reconnection (FR-5.5) applies. All values are in `main/config.h`. Before v1.8.4: "The system MUST detect when Wi-Fi is associated but no traffic gets through, and recover from it (detail of NFR-2.1). Every 60 s it pings the default gateway (3 pings). A check fails when Wi-Fi is associated and either has no IP address or the gateway does not answer; 3 failed checks in a row force a Wi-Fi reconnection. The watchdog only acts after the gateway has answered at least once, since some routers do not answer ping; while not associated, the usual reconnection (FR-5.5) applies. All values are in `main/config.h`." A router that occasionally ignored ping could then cause needless Wi-Fi reconnections while MQTT and the web page were working.
*   **NFR-2.4:** [v1.8.2] If the network is still down after 2 forced Wi-Fi reconnections, the system MUST restart; the history (FR-7.3) survives. To help diagnose such failures, the system logs the start reason at boot (power-on, software restart, watchdog, brownout...), logs a health line every 10 minutes (free heap, minimum free heap, largest free block, Wi-Fi signal, MQTT state, web requests served), and offers the console command `sys` with the uptime, start reason, [v2.0.0] device identifier, name, firmware version and sensor (FR-10.1 to FR-10.3), heap, Wi-Fi link, IP and gateway, watchdog state with the last sign of traffic and its source (since v1.8.4; before: last gateway reply), MQTT state and web requests served.

### 4.3 Maintainability
*   **NFR-3.1:** The code MUST be modular and easy to understand, divided into logical modules (header and source files) within the ESP-IDF `main` component.
*   **NFR-3.2:** It MUST be possible to configure the system simply by editing `config.h`.

### 4.4 Safety (Physical)
*   **NFR-4.1:** The system SHOULD be housed in an enclosure to protect the electronics from environmental influences (external, not part of this specification).

### 4.5 Usability (Display)
*   **NFR-5.1:** The displayed information MUST be comprehensible at a glance.

## 6. Interfaces

### 6.1 User Interface (OLED)
*   Display of temperature, humidity, and air pressure.
*   Date and time in the header once the clock is synchronized.
*   Wi-Fi signal icon at the right edge of the header.
*   Measurement icon (filled dot) at the left edge of the header, shown for 0.5 s after each measurement.
*   [v1.8.0] The BOOT button switches the display off and on; the display switches off after 5 minutes without a button press by default (see FR-9.1, FR-9.2).

### 6.2 Hardware Interfaces
*   **I2C bus:** Uses GPIO 21 (SDA) and GPIO 22 (SCL) of the ESP32.
*   **BOOT button:** [v1.8.0] GPIO 0 (active low), read by interrupt after start-up to switch the display. Held during a reset, it still selects the download mode of the ESP32.
*   **Power supply:** 3.3V for the ESP32, BME280, and SSD1306.

### 6.3 Serial Interface
*   The serial interface is used for debug output at 115200 baud (ESP-IDF console UART, viewed with `idf.py monitor`).
*   [v1.6.0] Interactive console on the same UART (prompt `weather> `): `help`, `log info`, `log dump [N]`, `log clear` (see FR-7.4, FR-7.5).
*   [v1.8.0] Console commands `display on`, `display off`, `display status` (see FR-9.1).
*   [v1.8.2] Console command `sys`: system health (see NFR-2.4); [v2.0.0] also device, name, firmware and sensor (see FR-10.1 to FR-10.3).
*   [v2.0.0] `log dump` prints the columns `device_id,sensor_id,seq,time,temperature_c,humidity_rh,pressure_hpa`; `log info` also shows the history format, the device and the sensors (see FR-10.6).

### 6.4 Network Interface
*   **Wi-Fi:** 2.4 GHz station mode (WPA2-PSK, or an open network if no password is set).
*   **Wi-Fi:** [v1.2.0] Add a symbol to indicate WiFi connectivity in the yellow area (see FR-5.7).
*   **Wi-Fi power save:** [v1.8.4] Off by default (`WIFI_POWER_SAVE` in `main/config.h`). With modem power save on (the ESP-IDF default up to v1.8.3), the station stopped receiving with some routers while it could still send; turning it on saves energy, which matters for a battery supply (section 3.9).
*   **Wi-Fi access point and link:** [v1.8.7] The station scans all channels and joins the access point with the strongest signal (a mesh offers the same network from several nodes; before v1.8.7 it joined the first one found). Each association is logged with network name, access point (BSSID), channel, channel width (HT20/HT40), security and signal. ~~A-MPDU aggregation on reception is off by default (`sdkconfig.defaults`): the station receives little data, and a mesh access point kept tearing the Block Ack sessions down.~~ [CHANGED v1.8.8] A-MPDU aggregation is on in both directions (ESP-IDF default). v1.8.7 turned it off on reception because the `DELBA reason:37, initiator:0(recipient)` messages were misread: they came from the access point as recipient, so they concerned the station's transmission, and they are harmless. [CHANGED v2.3.2] A-MPDU aggregation is off when sending (`# CONFIG_ESP_WIFI_AMPDU_TX_ENABLED is not set` in `sdkconfig.defaults`) and stays on for reception. At about -68 dBm the link stalled for up to 5 s and then delivered the held packets at once: a `ping` from the local network lost 40 to 60 % and the replies after a stall arrived together, 5.2, 4.2, 3.2, 2.2 and 1.2 s late; the web page did not load in either browser. Without aggregation on sending, the loss fell to 0 to 10 % with short peaks of about 1 s. The `DELBA` messages of v1.8.7 already concerned the station's sending. The station sends little data, so the lower peak throughput when sending does not matter; the CSV download (FR-8.5) may take longer. If stalls come back, the setting can be turned on again with `idf.py menuconfig` (Component config → Wi-Fi). Opening and closing Block Ack sessions (`ba-add`, `ba-del`, `DELBA reason:39` after inactivity) is routine; since v1.8.8 these Wi-Fi driver messages are no longer logged (driver log level WARN, `main/config.h`), while the association line above still is. [v1.8.9] Each disconnection is logged with the network, access point (BSSID), signal and the reason with its meaning (for example `reason 2, access point did not answer authentication`), so a failing access point can be identified without the driver messages. A signal of about -60 dBm or better is needed for a responsive web page; at -65 to -75 dBm the link loses packets and answers can take seconds.
*   **NTP:** SNTP client (UDP port 123), default server `pool.ntp.org`.
*   **MQTT:** [v1.5.0] Client publishing the weather data as JSON to the configured broker (TCP 1883 for `mqtt://`, 8883 for `mqtts://`), topic `weather-station/data` (see FR-6.1 to FR-6.6). [v1.8.4] Client ID `weather-station-` plus the last 3 bytes of the Wi-Fi MAC address (e.g. `weather-station-51a842`), shown when the client connects and by `sys`; before v1.8.4 the ESP-MQTT default `ESP32_` plus the same bytes. [CHANGED v2.0.0] Topics `weather-station/<device_id>/data` (readings) and `weather-station/<device_id>/info` (device, firmware, intervals, sensors; retained, sent on every connection and after a sensor change); the retained message on the former topic `weather-station/data` is cleared on every connection; client ID = device identifier (e.g. `ws-a0b76551a842`) (see FR-10.1, FR-10.4). [v2.1.0] Topic `weather-station/<device_id>/status`: `online` on connection, `offline` as last will (see FR-6.7). [v2.2.0] Data messages carry `rssi_dbm`, the lowest Wi-Fi RSSI since the previous message (see FR-5.8).

## 7. Open Issues / Future Extensions

*   **Calibration:** Provide a way to calibrate the sensor data.
*   **Hardware RTC:** Add an RTC module (e.g. DS3231) so the time of day survives power loss without Wi-Fi (the time of day via NTP is implemented in v1.1.0).
*   **Additional sensors:** Support a second sensor in the hardware and the drivers. The history format 2 (FR-10.6) and the identifiers (FR-10.3) already allow up to 254 sensors per station.
